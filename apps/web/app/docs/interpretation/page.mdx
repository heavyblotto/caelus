# Interpretation layer

Caelus calculates deterministic astronomical data (planetary positions,
aspects, house cusps, dignities, and geometric patterns) without bundling
interpretive prose. Keeping calculation separate from delineation allows the
numerical layer to remain verifiable against reference ephemerides while
letting applications choose any astrological tradition or writing style.

The interpretation layer provides a structured interface between validated
chart output and downstream interpretation logic: deterministic chart facts
come from the engine, narrative or rule text comes from your corpus or language
model, and citation IDs tie every claim back to verifiable chart geometry.

```text
Engine (validated)     chart(): bodies, aspects, angles, cusps
  → Fact projection    interpretationContext(chart): ranked, citable atoms
  → Matching           selectors over atoms (each match carries its provenance)
  → Sources            your rule corpus + interpret() / reconcile()
  → Output             a structured reading, or an LLM brief + citation audit
```

Each stage can be used independently: stop after fact projection to feed your
own pipeline, or connect the entire stack to generate citation-audited readings.

## Key use cases

- **Ground an LLM in verified calculations.** Language models write fluent
  astrological prose easily, but frequently fabricate planetary placements or
  aspects when asked to calculate charts themselves. Passing ranked fact atoms
  tagged with stable IDs and checking output with `auditCitations` ensures
  every interpretive claim rests on actual chart data.
- **Evaluate a rule corpus.** Encode your house style or tradition using
  selectors over the fact model (such as Mars in an angular house inside a
  T-square) and retrieve ranked entries alongside the exact facts that matched.
- **Prioritize and reconcile overlapping rules.** Salience weights surface
  prominent placements first, while `reconcile` groups rules touching the same
  placement and flags conflicting tags declared in your corpus.

## 1. Project a chart into fact atoms

`interpretationContext(chart)` flattens a `Chart` into a ranked array of typed
**fact atoms**, each representing an atomic statement ready for rule matching
or LLM citation:

<CodeBlock
  lang="typescript"
  label="atoms.ts"
  code={`import { Engine, julianDay, interpretationContext } from "caelus";
import { embeddedData } from "caelus/data-embedded";

const engine = new Engine(embeddedData);
const chart = engine.chartAt(julianDay(1990, 6, 10, 14, 30, 0), 27.95, -82.46, "placidus");

const ctx = interpretationContext(chart);
ctx.atoms.slice(0, 3).forEach((a) => console.log(a.id, ":", a.text));
// pattern:t_square:mars-moon-saturn : T-square: Mars, Moon, Saturn (apex Saturn)
// placement:moon : Moon in Capricorn, house 6
// aspect:moon~neptune:conjunction : Moon conjunction Neptune (applying, orb 0.6°)`}
/>

Every atom exposes five common properties:

- **`id`**: a deterministic, content-addressable identifier (`placement:mars`,
  `aspect:mars~saturn:square`, `pattern:t_square:mars-moon-saturn`,
  `signature:element:fire`, `angle:asc`). Downstream claims cite this ID to
  establish provenance.
- **`kind`**: `placement | aspect | pattern | signature | angle | angleContact |
  dispositor | reception | star | lot | degree | transit | transitHouse | station |
  synastry | composite | compositeAspect | timelord | dignity | nakshatra |
  varga | yoga |
  parallel | outOfBounds | return | lunation | solarPhase`.
- **`bodies`**: array of body IDs involved, for filtering and cross-reference.
- **`salience`**: an overridable prominence score (detailed below).
- **`text`**: a plain summary of the astronomical fact without interpretive
  framing (`"Moon conjunction Neptune (applying, orb 0.6°)"`).

**Reception** atoms record mutual reception by **domicile**, **exaltation**, or
sect **triplicity** (as well as mixed pairs such as `domicile-exaltation`).
Match them with `hasReception({ body: "venus" })`.

**Degree** atoms express each point's zodiacal position as an ordinal degree
(a planet at 14°30′ Aries occupies the *15th* degree of Aries) alongside its
ten-degree decan/face index (1–3). One atom is generated per body plus the
Ascendant and Midheaven; match with `hasDegree({ sign: "Aries", degree: 15 })`.

**Star** and **lot** atoms depend on catalog lookups and lot calculations that
sit outside the base `Chart` object, so supply them through `ContextOptions`:
tight conjunctions with fixed stars (`star:jupiter:Sirius` from
`Engine.starConjunctions`) and Hermetic lots (`lot:fortune` from
`Engine.lots`). Match with `hasStar({ star: "Algol" })` and
`hasLot({ lot: "fortune" })`.

**Parallel** and **out-of-bounds** atoms capture declination geometry absent
from ecliptic longitudes: bodies forming parallels while longitudinally
unaspected (`parallel:mars~venus:parallel`), or bodies whose declination exceeds
the obliquity of the ecliptic (`oob:moon`). Match with
`hasParallel({ between: ["mars", "venus"] })` and `hasOutOfBounds({ body: "moon" })`.

### Diachronic and synastry atoms

Extend a natal projection with transits, time-lords, Vedic factors, and
synastry via `ContextOptions` and two enrichment helpers:

- **`enrichContextOptions(engine, chart, target)`**: adds transits to natal
  (with phase and strength), active profection, zodiacal releasing, firdaria,
  and Vimshottari dasha periods, traditional term/face/triplicity/almuten facts,
  and nakshatra, D9, and yoga atoms when the chart uses a sidereal zodiac.
- **`enrichSynastryOptions(engine, chartA, chartB)`**: computes inter-chart
  aspects, house overlays, composite midpoint placements, and internal
  composite aspects (using chart A as the base). When both charts include
  valid birth times and angles, composite placements carry a **composite house**
  computed via `compositeFrame` (equal houses from the midpoint Ascendant,
  `method: "equal-from-midpoint-asc"`). If either chart lacks birth time angles,
  no synthetic house frame is invented and `hasComposite({ house })` matches
  nothing. Note that the averaged midpoint Midheaven does not generally align
  with the 10th equal-house cusp because independent angle averages do not
  preserve quadrant geometry.

Representative IDs include `transit:saturn~natal_moon:square`,
`profection:year:scorpio:mars`, `zr:l1:scorpio:mars`, `dasha:maha:saturn`,
`term:moon:saturn`, `synastry:mars~b_venus:square`, `composite:mars`,
`nakshatra:moon:Ashwini`, `varga:d9:moon:virgo`, and `yoga:Gajakesari`. Match
these using `hasTransit`, `hasTimelord`, `hasSynastry`, `hasComposite`,
`hasDignityFine`, `hasNakshatra`, `hasVarga`, and `hasYoga`. All IDs resolve
cleanly in `auditCitations`.

### Derived atoms beyond base Chart fields

Several standard interpretive factors do not live as standalone fields on
`Chart` (a planet conjunct an angle is not listed inside planetary aspects,
solar proximity is separate from sign dignities, and a return relates two
timestamps). `interpretationContext` derives these automatically as typed atoms:

- **`angleContact`** (`angleContact:sun:asc`): a planet within orb of the
  Ascendant, Descendant, Midheaven, or IC degree (distinct from general angular
  house occupancy; configurable via `angleOrb`, default 8°). Selector:
  **`hasAngleContact`**.
- **`transitHouse`** (`transitHouse:saturn:7`): identifies which natal house a
  transiting body currently traverses, regardless of aspect orbs. Selector:
  **`hasTransitHouse`**.
- **`station`** (`station:mercury:retrograde`): flags planets turning retrograde
  or direct near the chart timestamp (default ±5-day window). Selector:
  **`hasStation`**.
- **`return`** (`return:saturn:1`): flags planetary returns within orb and
  tracks cycle count so a first Saturn return is distinct from a second.
  Selector **`hasReturn`** accepts `nth` or `minNth`.
- **`lunation`** (`lunation:full:eclipse:lunar`): captures nearby New or Full
  Moons, eclipse status, natal house placement, and touched natal points.
  Selector **`hasLunation`** filters by phase, eclipse flag, house, and
  `onNatal`.
- **`solarPhase`** (`solarPhase:mercury:cazimi`): tags cazimi, combust, and
  under-the-beams status using standard electional orbs across natal and
  transit charts. Selector: **`hasSolarPhase`**.
- **`parallel`** and **`outOfBounds`** (`parallel:mars~venus:parallel`,
  `oob:moon`): declination aspects and out-of-bounds flags. Selectors:
  **`hasParallel`**, **`hasOutOfBounds`**.
- **`compositeAspect`** (`compositeAspect:mars~venus:square`): aspects between
  composite midpoint placements, capturing internal relationship geometry
  alongside individual `composite` placements. Selector:
  **`hasCompositeAspect`**.

To give rule authors consistent coverage, three projection behaviors diverge
slightly from the raw calculation APIs: `interpretationContext` computes aspects
to lunar nodes even though `findAspects` omits them, `transitAspects` accepts a
natal lunar node as a target, and classical planets holding zero essential
dignities receive a `"peregrine"` tag on their placement atom while
`Chart.bodies[id].dignities` remains unmodified.

<CodeBlock
  lang="typescript"
  label="enrich.ts"
  code={`import {
  interpretationContext, enrichContextOptions, enrichSynastryOptions,
  transitAspects, julianDay,
} from "caelus";

const targetJd = julianDay(2025, 6, 10, 12, 0);
const ctx = interpretationContext(chart, {
  stars, lots,
  ...enrichContextOptions(engine, chart, {
    jd: targetJd, lat: 27.95, lonEast: -82.46, zodiac: chart.zodiac,
  }),
});

// Or supply hits directly:
const transits = transitAspects(chart, engine, targetJd, { maxOrb: 3 });
interpretationContext(chart, { transits });`}
/>

Both the Playground **Reading** tab and the MCP **`chart_facts`** tool apply
`enrichContextOptions` automatically when `target_date` is provided. MCP
**`synastry`** returns matching citable atoms alongside a structured prompt
brief.

Type-specific properties attach directly to each atom: placement atoms carry
`sign`, `signDeg`, `house`, `retrograde`, and `dignities`; aspect atoms carry
`aspect`, `orb`, `phase`, and `strength`; pattern atoms carry `pattern` and
`apex`; signature atoms carry `facet` and `value`; dispositor atoms carry
`dispositor` and `final`; star atoms carry `body`, `star`, and `orb`; and lot
atoms carry `lot`, `sign`, and `house`.

Aspect atoms also propagate two properties computed on `Chart.aspects`:

- **`phase`**: `applying`, `separating`, or `exact`, computed from relative speed.
- **`strength`**: normalized proximity from `0` (at orb edge) to `1` (exact).

### Salience scoring

Salience ranks atoms so prominent factors surface first without encoding
astrological judgments. Total salience sums explicit weights that you can
customize via `ContextOptions.salience`:

| Contribution | Applies to |
|---|---|
| `base` | every atom |
| `luminary` | Sun or Moon involvement |
| `angular` | angular houses (1, 4, 7, 10) or angle atoms |
| `chartRuler` | Ascendant ruler's placement |
| `dignity` | per essential dignity held |
| `hardAspect` | conjunction, square, or opposition |
| `pattern` | aspect configuration |
| `dispositor` / `reception` | dispositor link / mutual reception |
| `star` / `lot` | fixed-star conjunction / Hermetic lot |
| `transit` / `transitHouse` / `station` | transit-to-natal aspect / transited natal house / nearby station |
| `synastry` / `composite` | inter-chart aspect or overlay / composite placement or aspect |
| `timelord` | active profection, ZR, firdaria, or dasha period |
| `dignityFine` | term, face, triplicity, or almuten fact |
| `vedic` | nakshatra, varga, or yoga fact |
| `parallel` / `outOfBounds` | declination parallel / body outside ecliptic obliquity |
| `planetReturn` / `lunation` / `solarPhase` | active return / nearby New or Full Moon (doubled on eclipses) / solar proximity state |

When supplying a full `SalienceWeights` literal rather than a `Partial<>`
override, include `planetReturn`, `lunation`, and `solarPhase` (added in 0.25.0).

Override any subset of weights through `ContextOptions.salience`:

<CodeBlock
  lang="typescript"
  label="salience-override.ts"
  code={`// Lead with configurations, mute the luminary bump.
const ctx = interpretationContext(chart, {
  salience: { pattern: 8, luminary: 0 },
});`}
/>

Because prominence weights represent application preferences rather than
astronomical constants, tests verify structural invariants (valid chart links,
unique atom IDs, and sort order) rather than pinning salience numbers to
external ephemerides.

## 2. Match atoms with selectors

A **selector** evaluates an `InterpretationContext` and returns all atoms that
justify a match. Unlike time-search predicates in [`when()`](/docs/recipes),
selectors can inspect houses, dignities, configuration membership, chart
signatures, aspect phase, and normalized strength:

<CodeBlock
  lang="typescript"
  label="selectors.ts"
  code={`import {
  hasPlacement, hasAspect, hasPattern, hasSignature, hasAngle,
  hasDispositor, hasReception, hasStar, hasLot, hasDegree,
  hasTransit, hasTimelord, hasSynastry, hasComposite,
  hasDignityFine, hasNakshatra, hasVarga, hasYoga,
  matchAll, matchAny, matchNone,
} from "caelus";

// Atom selectors take a filter; any omitted field is a wildcard.
hasPlacement({ body: "mars", house: 10 });        // Mars in the 10th
hasAspect({ between: ["moon", "neptune"], aspect: "conjunction" });
hasAspect({ a: "saturn", phase: "applying", minStrength: 0.5 });
hasPattern({ kind: "t_square", body: "mars" });
hasSignature("element", "fire");
hasReception({ body: "venus" });
hasStar({ star: "Algol" });                       // any body conjunct Algol
hasLot({ lot: "fortune", house: 1 });             // Part of Fortune rising
hasDegree({ sign: "Aries", degree: 15 });         // any point in the 15th degree of Aries
hasTransit({ transit: "saturn", natal: "moon", aspect: "square" });
hasTimelord({ system: "profection", level: "year" });

// Combinators compose them. matchAll unions the atoms that justified the match.
const angularMarsInTSquare = matchAll(
  hasPlacement({ body: "mars", house: 10 }),
  hasPattern({ kind: "t_square", body: "mars" }),
);

const m = angularMarsInTSquare(ctx);
// m.matched === true; m.atoms holds the placement + pattern atoms (the provenance)`}
/>

`matchAll` requires every child selector to match and merges their supporting
atoms; `matchAny` succeeds when any child matches and returns atoms from the
matching branches; and `matchNone` verifies that a selector matches nothing
(contributing zero atoms).

## 3. Connect a rule corpus

A **`Rule`** pairs a selector (`when`) with response prose (`text`), grouped
into an **`InterpretationSource`**. Running `interpret(ctx, sources)` evaluates
all rules and returns sorted `ReadingEntry` records containing the text,
matched `atomIds`, and total salience (`sum(atom.salience) * rule.weight`).

Note that the sample rules below are simplified placeholders illustrating the
corpus schema rather than finished delineation copy.

For a pre-built corpus, install **`caelus-delineations-pd`**, which structures
hundreds of public-domain delineations (planet-in-sign, house placements,
aspects, rising signs, and fixed stars) into validated selectors. Pass its
`sources` (or strict `publicDomainSources`) directly into `interpret()`. See
[Building a corpus](/docs/corpus) for extraction workflows, test harnesses, and
corpus licensing.

<CodeBlock
  lang="typescript"
  label="corpus.ts"
  code={`import { interpret, reconcile, hasPlacement, hasAspect, hasReception, matchAll, hasPattern } from "caelus";

const source = {
  id: "example",
  version: "0.1",
  rules: [
    {
      id: "moon-neptune",
      when: hasAspect({ between: ["moon", "neptune"], aspect: "conjunction" }),
      text: "Feeling and imagination blur together.",
      weight: 1.5,
      tags: ["water"],
    },
    {
      id: "saturn-domicile",
      when: hasPlacement({ body: "saturn", dignity: "domicile" }),
      text: "Saturn is structurally strong here.",
      tags: ["affirming"],
    },
    {
      id: "venus-reception",
      when: hasReception({ body: "venus" }),
      // text can be a function of the match, for templating from the atoms
      text: (m) => "Venus is in mutual reception (" + m.atoms[0].id + ").",
    },
  ],
};

const reading = interpret(ctx, [source]);
reading.entries.forEach((e) => console.log(e.salience.toFixed(1), e.text, e.atomIds));`}
/>

### Reconciling overlapping rules

Because flat ranked lists often spread commentary about one planet across
multiple entries, `reconcile` clusters rules sharing identical `atomIds`,
deduplicates identical text, and flags a group as `contested` whenever
mutually opposing tags defined by the corpus author (via `tags` and
`conflicts`) appear together:

<CodeBlock
  lang="typescript"
  label="reconcile.ts"
  code={`const groups = reconcile(reading, {
  dedupe: true,
  conflicts: [["affirming", "challenging"]],
});

for (const g of groups) {
  console.log(g.atomIds.join(", "), g.contested ? "(contested)" : "");
  for (const e of g.entries) console.log("  -", e.text);
}`}
/>

## 4. Produce a rule reading or grounded LLM prompt

Consume an `InterpretationContext` in either of two ways:

1. **Deterministic rule reading**: pass `interpret()` or `reconcile()` groups
   directly to your UI alongside their provenance `atomIds`.
2. **Citation-audited LLM prompt**: pass the context to `chartBrief(ctx, opts)`
   to format salience-ranked, bracketed `[id]` facts into a prompt. Instruct the
   model to cite `[id]` tags behind each claim, then call `auditCitations` to
   verify that every cited ID exists in the context:

<CodeBlock
  lang="typescript"
  label="brief.ts"
  code={`import { chartBrief, auditCitations } from "caelus";

// Cap to the 20 most salient facts; optionally fold the rule reading in.
const brief = chartBrief(ctx, { limit: 20, reading });
console.log(brief.prompt);
// Natal chart facts follow, each with a stable id in [brackets]. Interpret them
// in your own words; after each statement, cite the id(s) it rests on as [id]...
//
// [pattern:t_square:mars-moon-saturn] T-square: Mars, Moon, Saturn (apex Saturn)
// [placement:moon] Moon in Capricorn, house 6
// [aspect:moon~neptune:conjunction] Moon conjunction Neptune (applying, orb 0.6°)
// ...

// ...send brief.prompt to your model, collect its claims + the ids each cited...
const modelClaims = [
  { text: "The Saturn T-square asks for discipline.", cites: ["pattern:t_square:mars-moon-saturn"] },
  { text: "Venus square Pluto drives obsession.", cites: ["aspect:venus~pluto:square"] }, // invented
];

const audit = auditCitations(modelClaims, ctx);
// audit.ok === false; audit.unknown === ["aspect:venus~pluto:square"]
// the second claim cited a fact that is not in the chart`}
/>

`auditCitations` returns whether all references resolve (`ok`), counts of
`cited` vs. `uncited` claims, and arrays of `valid` and `unknown` IDs. Any
`unknown` ID flags a claim referencing a placement or aspect absent from the
computed chart.

## 5. Pass provenance for uncertain or symbolic charts

When working with forecasts, fictional subjects, or rounded birth times, pass
the chart's `Realm` and time `Certainty` from `realize()` into
`interpretationContext`:

<CodeBlock
  lang="typescript"
  label="realize-to-brief.ts"
  code={`import {
  Engine, realize, interpretationContext, chartBrief,
} from "caelus";
import { embeddedData } from "caelus/data-embedded";

const engine = new Engine(embeddedData);
const realized = realize(engine, {
  realm: "forecast",
  when: { kind: "range", earliest: "2030-01-01", latest: "2030-12-31" },
  where: { kind: "geo", lat: 40.7, lonEast: -74.0 },
});
if (!realized.chart) throw new Error(realized.note);

const ctx = interpretationContext(realized.chart, {
  provenance: {
    realm: realized.realm,
    certainty: realized.time.certainty,
  },
});
const brief = chartBrief(ctx, { limit: 20 });`}
/>

When `certainty` is weaker than `exact`, time-sensitive atoms (lunar positions
and chart angles) are down-weighted (`0.7` for `approximate`, `0.6` for
`representative`) while slower planetary placements keep full weight.
`chartBrief` also prepends a framing notice indicating provisional forecast
language, symbolic rather than biographical interpretation, or warning against
relying on houses and angles for uncertain birth times. See the{" "}
[Provenance guide](/docs/provenance) for full anchor and realm options.

## Using over MCP

For LLM clients that already handle prose generation (Claude Desktop, Cursor,
or custom agents), the [MCP server](/docs/mcp) exposes `chart_facts`. Passing
birth data (plus optional `when` anchors, `anchors` registry, `realm`,
`constraints`, `target_date`, or `include_vedic`) returns the ranked fact atoms
alongside a ready-to-use `brief`, and `synastry` outputs atoms and a
brief comparing two charts:

```text
"Read my natal chart: born June 10 1990, 2:30pm, Tampa FL."
  → chart_facts → ranked facts + brief → the host writes prose, citing [ids]
```

## Choosing an entry point

- **`interpretationContext` only**: use when you have your own UI or LLM
  workflow and simply need normalized, ID-addressable chart facts.
- **`interpret` and `reconcile`**: use when building a deterministic rule engine
  that needs provenance links and conflict tagging.
- **`chartBrief` and `auditCitations`**: use when sending chart data to an LLM
  and verifying that every generated statement cites real placements.
- **`realize` with provenance metadata**: use when handling forecasts, fiction,
  archetypes, or approximate times so salience damping and framing match how the
  chart was constructed.
