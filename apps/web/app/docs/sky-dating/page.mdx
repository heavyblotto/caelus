# Sky dating

A chart goes from an instant to positions. `dateSky` goes the other way: you
describe where the planets stood, and it returns every window in a date range
in which that description was true. This is the computation used to date a
horoscope that records positions and no year.

The [Sky Dating instrument](/instruments/sky-dating) runs the same search in
the browser, with the funnel drawn as a timeline.

```ts
import { Engine, dateSky, julianDay, calendarDate } from "caelus";
import { loadNodeData } from "caelus/node";

const engine = new Engine(loadNodeData("node_modules/caelus/data"));

const { windows, funnel } = dateSky(engine, [
  { body: "jupiter", sign: "Pisces" },
  { body: "venus", sign: "Taurus" },
  { body: "saturn", sign: "Cancer" },
  { body: "mars", sign: "Gemini" },
], julianDay(-800, 1, 1, 0, 0, 0, "julian"), julianDay(0, 1, 1, 0, 0, 0, "julian"));

windows.map((w) => calendarDate(w.start, "julian"));
```

Those four signs are the positions usually quoted for the oldest surviving
Babylonian horoscope, which A. Sachs dated to 29 April 410 BCE ("Babylonian
Horoscopes", *Journal of Cuneiform Studies* 6, 1952). Across the 800 years
searched, three windows match:

| Window opens (Julian calendar) | Length |
|---|---|
| 25 June 529 BCE | 6.3 days |
| 16 April 410 BCE | 24.5 days |
| 23 March 173 BCE | 19.9 days |

The second window contains Sachs's date. Four planets named by sign leave
three candidates in eight centuries, and any further detail in a text, such as
the Moon's sign or a month name, picks one. The signs on this page have not
been checked against the printed edition of the tablet, so treat the example
as a demonstration of the method.

## Years and calendars

Windows are UT Julian Days. `julianDay` takes a seventh argument, `"julian"`,
for a date written in the Julian calendar, which is how historical dates
before 15 October 1582 are given. `calendarDate(jd, "julian")` reads one back.
Years are astronomical, so year `0` is 1 BCE and year `-409` is 410 BCE.

## Constraints

Each constraint names a quantity and the arc it must lie in.

| Constraint | Meaning |
|---|---|
| `{ body: "saturn", sign: "Libra" }` | A body in a zodiac sign, by name or by index 0 to 11 |
| `{ body: "mars", lon: 112.5, orb: 2 }` | A body within an orb of a longitude |
| `{ body: "venus", from: 350, to: 15 }` | A body in the arc running forward from one longitude to another |
| `{ elongation: ["moon", "sun"], from: 180, to: 360 }` | The Moon's longitude minus the Sun's, here a waning Moon |

Add `pad` to a constraint to widen its arc by that many degrees on both sides,
or pass `pad` in the options to widen every arc. The `zodiac` option measures
longitudes in any zodiac the engine supports, such as
`"sidereal:fagan_bradley"`.

## When the source's signs are not the engine's

The horoscope of the emperor Hadrian survives in Hephaestio of Thebes, who
took it from Antigonus of Nicaea. It places the Sun, the Moon, and Jupiter in
Aquarius, Saturn and Mercury in Capricorn, and Venus and Mars in Pisces.
Neugebauer and Van Hoesen (*Greek Horoscopes*, 1959, no. L 76) date it to 24
January 76 CE.

For that morning the engine's tropical positions are the Moon at 26°
Capricorn, Jupiter at 26.5° Capricorn, and Saturn at 29.9° Sagittarius. Each
is a few degrees short of the sign the text names, because Greek horoscopes of
the period measured longitude in a zodiac offset from the tropical one. A pad
absorbs the offset:

```ts
const hadrian = dateSky(engine, [
  { body: "sun", sign: "Aquarius" },
  { body: "moon", sign: "Aquarius" },
  { body: "jupiter", sign: "Aquarius" },
  { body: "saturn", sign: "Capricorn" },
  { body: "mercury", sign: "Capricorn" },
  { body: "venus", sign: "Pisces" },
  { body: "mars", sign: "Pisces" },
], julianDay(-2990, 1, 1, 0, 0, 0, "julian"), julianDay(2990, 1, 1), { pad: 6 });
```

Across those 5,980 years, with every sign widened by 6°, four windows match.
They open on 4 March 2485 BCE, 23 February 2248 BCE, 3 February 1394 BCE, and
24 January 76 CE. The last runs from 00:49 UT on 24 January to 20:30 UT on 26
January, and no other window falls within a thousand years of it. The search
took 1.2 seconds in Node on a laptop.

## The funnel

`dateSky` scans the slowest body across the whole range, then scans each
faster body only inside the windows that survive. `funnel` reports the
constraints in scan order with what was left after each. For the Hadrian
search:

| Constraint | Windows left | Days left |
|---|---|---|
| Saturn in Capricorn | 432 | 269,787 |
| Jupiter in Aquarius | 150 | 29,603 |
| Sun in Aquarius | 134 | 4,427 |
| Mars in Pisces | 34 | 768 |
| Venus in Pisces | 19 | 292 |
| Mercury in Capricorn | 11 | 121 |
| Moon in Aquarius | 4 | 10 |

The funnel shows which constraint did the work. It also shows where a search
that returns nothing ran dry, which points at the position in a text most
likely to be miscopied.

## In the browser

The embedded tier covers 1000 to 3000, so a search inside that span needs no
data files and runs where the page is. This one asks when the seven classical
bodies were all in Aquarius, between 1800 and 2200:

```ts run
import { Engine, dateSky, julianDay, calendarDate } from "caelus";
import { embeddedData } from "caelus/data-embedded";

const engine = new Engine(embeddedData);

const { windows } = dateSky(engine, [
  { body: "sun", sign: "Aquarius" },
  { body: "moon", sign: "Aquarius" },
  { body: "mercury", sign: "Aquarius" },
  { body: "venus", sign: "Aquarius" },
  { body: "mars", sign: "Aquarius" },
  { body: "jupiter", sign: "Aquarius" },
  { body: "saturn", sign: "Aquarius" },
], julianDay(1800, 1, 1), julianDay(2200, 1, 1));

windows.map((w) => [calendarDate(w.start), calendarDate(w.end)]);
```

One window matches. It opens at 22:56 UT on 3 February 1962 and closes at
22:52 UT on 5 February, and `calendarDate` gives each hour as a decimal. The
Moon crosses a sign in a little over two days, which sets the length. The
search takes half a second in Node on a laptop. The
[Sky Dating instrument](/instruments/sky-dating) runs the same function behind
a form.

## The full packs in the instrument

The instrument starts on the embedded tier. Its Data control switches to the
full packs: it lists the files the current search needs and their size, and it
downloads them when the search is run. Each file is checked against a SHA-256
before it is used. [Deep Time](/docs/deep-time) describes the loader.

| Preset | Files | Download | Search, full packs | Search, embedded |
|---|---|---|---|---|
| Babylonian tablet, 800 years | 5 | 4.2 MB | 0.1 s | 0.6 s |
| Horoscope of Hadrian, 5,997 years | 14 | 27.2 MB | 1.1 s | 4.5 s |

Both tiers find the same windows, and the edges move. For the Babylonian
tablet the embedded tier's edges differ from the full packs' by up to about 6
minutes. For the horoscope of Hadrian they differ by up to about 27 minutes,
and the largest difference is at the oldest window:

| Window opens, full packs | Embedded tier opens | Embedded tier closes |
|---|---|---|
| 4 March 2485 BCE, 07:55 UT | 13 minutes earlier | 27 minutes earlier |
| 23 February 2248 BCE, 16:10 UT | 11 minutes earlier | 10 minutes earlier |
| 3 February 1394 BCE, 12:22 UT | 6 minutes earlier | 6 minutes earlier |
| 24 January 76 CE, 00:49 UT | 1 minute earlier | 1 minute earlier |

The full packs are also the faster tier, because a fitted polynomial costs
less to evaluate than the series it replaces. The times are from one laptop.

## From an AI client

The MCP server exposes the same search as the `date_sky` tool. It takes the
constraints with `start_year` and `end_year` in astronomical years, and it
returns each window with calendar dates already worked out: the Julian
calendar before 15 October 1582, and an `era` label such as `410 BCE`. A local
`caelus-mcp` loads the era packs and reaches the classical era. The hosted
endpoint runs the embedded tier and covers 1000 to 3000, and it refuses a
wider span with the years it does cover. Setup is in the
[MCP guide](/docs/mcp).

## Limits

- The range must lie inside the data the engine was built with. Dates before
  1000 CE are validated only with the era packs. `loadNodeData` loads them in
  Node, and a browser fetches them with `loadPacks`; the embedded tier does
  not include them. `engineCapabilities` reports each body's span.
- Chiron and the asteroids have no pack before 1600, so a constraint on one
  of them cannot be searched earlier than that.
- Constraints are on longitude. There is no constraint yet for the Ascendant,
  for a house, or for a retrograde flag. [`when()`](/docs/api) accepts
  arbitrary predicates and is the better tool across years or decades; it
  samples the whole range at one step, which is too slow across millennia.
- A window with the Moon in it is two or three days long. ΔT is uncertain by
  minutes in antiquity, which moves the Moon by arcminutes and shifts a
  window's edges by a similar number of minutes. It does not move a window to
  another date.
