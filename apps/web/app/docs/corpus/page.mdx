# Building a corpus

The [interpretation layer](/docs/interpretation) establishes the typed boundary
between chart geometry and written delineations. The companion package
**`caelus-delineations-pd`** implements that contract using hundreds of
public-domain passages compiled into verified chart selectors and provenance
records.

While `caelus` handles rule evaluation (`interpret()`) and citation audits,
`caelus-delineations-pd` provides curated text passages, bibliographic tracking,
and test assertions confirming that every compiled selector matches its exact
target atoms. (The Playground **Reading** tab runs the separate in-repo
`caelus-corpus` essays, while `caelus-delineations-pd` is the published
npm reference corpus.)

## Consuming an existing corpus

Install the companion package:

<CodeBlock lang="bash" code="npm install caelus-delineations-pd" />

Project a `Chart` to fact atoms and evaluate the compiled rule sources:

<CodeBlock
  lang="typescript"
  label="consume.ts"
  code={`import { Engine, julianDay, interpretationContext, interpret,
  enrichContextOptions } from "caelus";
import { loadNodeData } from "caelus/node";
import { sources, publicDomainSources } from "caelus-delineations-pd";

const engine = new Engine(loadNodeData(dataDir));
const chart = engine.chartAt(julianDay(1990, 6, 10, 14, 30, 0), 27.95, -82.46, "placidus");

const ctx = interpretationContext(chart, {
  ...enrichContextOptions(engine, chart, {
    jd: julianDay(2025, 6, 10, 12, 0), lat: 27.95, lonEast: -82.46,
  }),
});

// All sources (includes Llewellyn George Mercury–Saturn sign cells, tagged gratis-not-pd)
const reading = interpret(ctx, sources);

// Strict public-domain only: drops the George source
const pdReading = interpret(ctx, publicDomainSources);

reading.entries.forEach((e) => console.log(e.salience.toFixed(1), e.text, e.atomIds));`}
/>

Each returned `ReadingEntry` includes the source prose, an `atomIds` provenance
list, and an aggregated salience score.

### Including fixed stars and lots

Because fixed-star conjunctions and Hermetic lots are separate from the base
`Chart` object, generate them explicitly and pass them to
`interpretationContext` before calling `interpret()`:

<CodeBlock
  lang="typescript"
  label="enrich.ts"
  code={`const stars = engine.starConjunctions(chart, { orb: 1 });
const lots = engine.lots(chart);

const ctx = interpretationContext(chart, { stars, lots });
const reading = interpret(ctx, sources);`}
/>

The MCP `chart_facts` tool includes Fortune, Spirit, tight fixed-star
conjunctions, and optional transits and time-lords automatically. Application
code can replicate that enrichment with `enrichContextOptions` and
`enrichSynastryOptions`:

<CodeBlock
  lang="typescript"
  label="diachronic.ts"
  code={`import { enrichContextOptions, enrichSynastryOptions, julianDay } from "caelus";

const targetJd = julianDay(2025, 6, 10, 12, 0);
const ctx = interpretationContext(chart, {
  stars, lots,
  ...enrichContextOptions(engine, chart, {
    jd: targetJd, lat, lonEast: lon, zodiac: chart.zodiac,
  }),
});

// Synastry/composite on chart A as base:
interpretationContext(chartA, {
  ...enrichSynastryOptions(engine, chartA, chartB),
});`}
/>

### Additional package exports

| Export | Description |
|---|---|
| `sources` / `publicDomainSources` | Compiled `InterpretationSource[]` arrays ready for `interpret()` |
| `passages` / `passageSets` | Raw `PassageRecord` JSON objects organized by source work |
| `corpusManifest` | Bibliographic metadata (`sources/manifest.json`) |
| `correspondences` | Liber 777 table (Crowley public domain via open_777) |
| `selectorFromSpec` / `compileSource` | Utilities to compile custom passage files into runtime rules |

See the [Interpretation guide](/docs/interpretation) for selector filters,
conflict reconciliation, and LLM prompt briefs.

## Corpus build pipeline

Corpora store rules as serializable JSON data rather than handwritten
TypeScript selectors so provenance stays easy to audit:

```text
sources/manifest.json       bibliography + fetch specs + rights tags
  → sources/text/*.txt        public-domain scans (manifest-driven fetch)
  → scripts/extract/*.ts      parse enumerated delineations → PassageRecords
  → data/passages/*.json      passage + SelectorSpec + provenance
  → src/compile.ts            SelectorSpec → live Selector → Rule
  → src/sources.ts            one InterpretationSource per work → sources
```

Each **`PassageRecord`** binds a single attributed statement to an engine selector:

- **`when`**: a JSON-serializable **`SelectorSpec`** naming the target placement,
  aspect, configuration, angle, star, or lot.
- **`text`**: cleaned excerpt prose.
- **`atomIds`**: expected engine atom IDs (such as `placement:mars` or
  `aspect:moon~neptune:conjunction`), verified against live projections in CI.
- **`source`**: author, title, and optional section reference.
- **`rights`**: copyright classification (`pd-us`, `cc0`, or `gratis-not-pd`).

Storing selectors as JSON data and instantiating them via `selectorFromSpec()`
keeps corpora declarative, serializable, and safe to validate without executing
untrusted code.

### Supported `SelectorSpec` kinds

| `kind` | Example spec | Matches |
|---|---|---|
| `placement` | `{ body: "mars", sign: "Aries" }` | Mars in Aries |
| `placement` | `{ body: "moon", house: 10 }` | Moon in the 10th house |
| `aspect` | `{ a: "moon", b: "neptune", aspect: "conjunction" }` | Moon conjunct Neptune |
| `angle` | `{ angle: "asc", sign: "Leo" }` | Leo rising |
| `star` | `{ body: "jupiter", star: "Sirius" }` | Jupiter conjunct Sirius |
| `lot` | `{ lot: "fortune", house: 1 }` | Part of Fortune in the 1st house |
| `pattern` | `{ pattern: "t_square", body: "mars" }` | Mars participating in a T-square |
| `signature` | `{ facet: "element", value: "fire" }` | Fire dominant element |

Use title-case sign names (`"Aries"` rather than `"aries"`) and standard
snake-case body IDs (`"mean_node"`, `"true_node"`).

## Writing an extractor

Extractors live under `packages/caelus-delineations-pd/scripts/extract/`. Each
script parses one text source by structural markers (chapter headings, numbered
lists, or aspect tables), cleans OCR artifacts, and writes
`data/passages/<work>.json`.

Following the Saint-Germain Sun-sign extractor pattern:

1. **Match section headings deterministically** using explicit regexes matched
   to the edition's typography (such as `1. ARIES. (The …)`), avoiding fragile
   NLP guesswork.
2. **Normalize OCR text** via `denoise()` to strip page headers, footers, and
   line-break hyphenation.
3. **Emit one `PassageRecord` per entry** with `id`, `when`, `text`, `atomIds`,
   `source`, and `rights`.
4. **Register the script in `npm run extract`** inside the package configuration.

<CodeBlock
  lang="typescript"
  label="passage-record.ts"
  code={`{
  "id": "saint-germain:sun:aries",
  "when": { "kind": "placement", "body": "sun", "sign": "Aries" },
  "atomIds": ["placement:sun"],
  "text": "People born under this sign are…",
  "tradition": "modern",
  "source": { "author": "Saint-Germain", "work": "Practical Astrology", "locus": "Ch. 1" },
  "rights": "pd-us"
}`}
/>

When scanned tables resist automated parsing (due to astrological
glyph fonts or damaged verse blocks), test reports flag missing cells so you
can curate them manually (as done for Robson's fixed-star entries).

### Adding a source to the manifest

Add a bibliographic and fetch record inside `sources/manifest.json`:

<CodeBlock
  lang="json"
  label="manifest-entry.json"
  code={`{
  "id": "saint-germain-practical",
  "layer": 1,
  "title": "Practical Astrology",
  "author": "Comte de Saint-Germain",
  "year": 1901,
  "tradition": "modern",
  "rights": "pd-us",
  "file": "saint-germain-practical-astrology.txt",
  "fetch": { "url": "https://…", "stripGutenberg": true }
}`}
/>

Run `npm run fetch` to download source texts, `npm run extract` to rebuild JSON
passages, `npm run build` to compile exports, and `npm test` to run validation.

## Validation test suite

Running `npm test` in `caelus-delineations-pd` verifies structural integrity and
selector precision across the corpus:

- Every compiled rule resolves to a supported selector type.
- Every selector matches its target placement and triggers only when that
  condition holds (catching overly broad rules).
- Cited `atomIds` match real engine output atoms with zero invented IDs.
- Manifest entries, source checksums, and rights fields are complete.

Running against live `interpretationContext` output ensures any upstream schema
change or broken extractor fails CI immediately. Extend test cases whenever you
introduce a new passage shape.

## Licensing and rights tagging

Each work in `sources/manifest.json` carries an explicit `rights` tag:

| `rights` | Meaning |
|---|---|
| `pd-us` | Public domain in the United States for the cited edition/translation |
| `cc0` | Dedicated to the public domain via CC0 |
| `gratis-not-pd` | Available free to read online, with uncertain copyright status |

Because Llewellyn George's *A to Z* provides the cleanest OCR coverage across
Mercury–Neptune sign cells while holding an uncertain copyright status, it is
isolated under `gratis-not-pd` in `sources`; import `publicDomainSources` if
your application requires strict US public-domain licensing.

Full raw source scans remain local to the monorepo and are excluded from npm
tarballs, which publish only compiled passages and metadata.

## Current coverage

The reference package contains 372 compiled passages across eight sources:
planet-in-sign (Sun through Neptune), planet-in-house (Alan Leo),
planet-aspect-planet and planet-parallel-planet (Heindel), rising signs
(Heindel), curated fixed-star conjunctions (Robson), and Moon-in-nakshatra
delineations (all 27 mansions from *Brihat Jataka* ch. XVI). Selectors for
dignities and lots are supported in schema and await source texts. See the
package README for complete coverage tables.

## Fixed stars in embedded bundles

Because `caelus/data-embedded` bundles the fixed-star catalog,
`new Engine(embeddedData)` supports `starNames()`, `starConjunctions()`, and
Robson `star:*` rules in browsers, edge routes (`/api/chart`, hosted MCP), and
Node.js alike without calling `loadNodeData()`. Pass
`engine.starConjunctions(chart, { orb: 1 })` to `interpretationContext()` (as
MCP `chart_facts` does) to include star atoms in readings.
