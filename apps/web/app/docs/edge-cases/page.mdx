# Edge Cases & Stability

Review these boundary behaviors and compatibility commitments before shipping
Caelus in a production application.

## Supported date range

Planetary, lunar, and Pluto positions are validated across **1000–3000** using
Chebyshev packs fitted to JPL Horizons. Small bodies (asteroids and Chiron)
span **1600–2484**, matching the widest interval Horizons provides. Because the
hosted edge endpoint bundles only the compact Moon tier, it accepts a narrower
window and returns HTTP `400` outside it:

<CodeBlock
  lang="json"
  label="GET /api/chart?date=1500-01-01"
  code={`{ "error": "date out of this endpoint's embedded tier (1920-2080); the engine validates 1000-3000" }`}
/>

`chart()` does not throw when a timestamp falls outside a body's fitted span:
excluded bodies are omitted from `chart.bodies`, recorded in
`chart.unavailable`, and accompanied by a chart warning. (`position()` on a
single out-of-range body does throw `RangeError`.) Always check
`chart.unavailable` before indexing a body, and treat out-of-range warnings on
modern dates as a likely sign of an upstream date-parsing or timezone bug.

## East-positive longitude convention

Caelus follows the standard geographic convention of **east-positive**
longitudes: New York is `-74.0`, and Tokyo is `+139.7`. Many older astrology
libraries expect west-positive longitudes, so passing an unflipped sign silently
places the chart on the opposite side of Earth. The REST endpoint rejects
values outside `[-180, 180]` and documents the convention in its error message.

## Local time vs. UTC

The core engine expects **UT calendar components** and performs no timezone
conversion. Convert civil times yourself or use [`caelus-birth`](/docs/quickstart)
to resolve an IANA timezone from geographic coordinates. Watch out for two
daylight saving transitions that require explicit handling:

- **Nonexistent times** (spring-forward gaps, such as 02:30 AM on a DST start
  morning) never occurred on the clock: reject them or snap to the transition
  boundary.
- **Ambiguous times** (fall-back overlaps) map to two distinct UT timestamps:
  prompt the user to pick the earlier or later offset rather than silently
  guessing.

## Polar house fallback

Placidus and Koch houses are mathematically undefined inside the polar circles
(`|lat| ≳ 66°`, or wherever the Midheaven's degree never rises or sets). Instead
of throwing an error or returning corrupted cusps, `chart()` falls back to
whole-sign houses and records what happened:

<CodeBlock
  lang="typescript"
  label="polar.ts"
  code={`const chart = engine.chart(2024, 1, 1, 12, 0, 0, 78.22, 15.65, "placidus"); // Svalbard

chart.houseSystem;          // "whole_sign" — Placidus undefined this far north
chart.houseSystemRequested; // "placidus"`}
/>

Compare `chart.houseSystem` with `chart.houseSystemRequested` to detect when a
fallback occurred. Non-quadrant systems (`porphyry`, `equal`, and `whole_sign`)
never fall back.

## Circumpolar rise and set

During polar day or polar night, a celestial body may never cross the local
horizon, causing `riseSet` to return `null`. Because `null` also signals that no
event occurred within the search window, always guard against it:

<CodeBlock
  lang="typescript"
  label="riseset.ts"
  code={`const t = riseSet(engine, "sun", jd, 78.22, 15.65, "rise");
if (t === null) {
  // polar day/night, or no rise within the searched window
}`}
/>

## Event-search windows

Event searches operate inside an explicit `[start, end]` range and respect each
body's fitted span (1000–3000 for planets, Pluto, and the Moon; 1600–2484 for
asteroids and Chiron). An empty array simply means zero matches inside that
interval, so widen your bounds if needed. Because retrograde loops can produce
multiple exact crossings or returns in quick succession, search functions
return arrays of timestamps rather than single dates.

## Missing data packs

When optional data files are absent on disk, `loadNodeData` degrades **per
body** to the embedded dataset instead of failing. Bodies defined exclusively
in external packs (asteroids, Uranian points, and deep-field stars) become
unavailable, while core planets continue computing at embedded precision. See
[Data Tiers](/docs/data-tiers) for details on pack coverage.

## Floating-point output across runtimes

Raw floating-point results from JavaScript runtimes are not bitwise identical.
The ECMAScript specification leaves rounding behavior for transcendental
functions (`Math.sin`, `Math.atan2`, `Math.exp`, and others) to the host runtime,
and engines ship slightly different math libraries. Even between Node.js and
workerd (Cloudflare Workers), both based on V8, 17 of 22 tested `Math` functions
produced different lowest-order bits across 20,000 test inputs.

In practice, these rounding differences stay tiny. Across six benchmark charts
compared between Node.js and workerd, between 7 and 19 of roughly 160 numeric
fields differed in their final 1–2 mantissa bits while all keys, strings, and
arrays stayed identical. The maximum difference observed was 1.1e-12 degrees
(roughly four billionths of an arcsecond), more than eight orders of magnitude below the
engine's one-arcsecond validation floor. On the 1990-06-10 14:30 UT Tampa chart,
the largest discrepancy was 5e-14 degrees.

Because low-order bits vary across runtimes, avoid hashing raw float
responses, diffing them byte-for-byte, or using them directly as cross-runtime
cache keys. Compare values with a small numeric tolerance, or enable
[Canonical Mode](/docs/canonical), which quantizes positions onto an integer
grid so payloads and digests stay bitwise identical across runtimes and
languages. (Note that `/api/chart` returns raw floating-point JSON dependent on
the worker runtime.)

## Versioning and API stability

All four core packages (`caelus`, `caelus-mcp`, `caelus-birth`, `caelus-wheel`)
publish in **lockstep** at matching version numbers. Keep them pinned together
and avoid mixing minor versions across packages.

Pre-1.0 releases follow **semver-zero** conventions: minor bumps (`0.x.0`) may
introduce breaking changes, while patch bumps (`0.x.y`) stay backwards
compatible. These interfaces are intended to remain stable through 1.0:

- Core calculation APIs: `new Engine(data)`, `chart()`, `chartAt()`,
  `position()`, `longitude()`, `when()`, event-search functions, and
  `julianDay()`.
- Standard data loaders: `embeddedData` and `loadNodeData()`.
- Primary result shapes (`Chart`, `Position`): future additions will be purely
  additive.

Surfaces still iterating before 1.0 include derived charts (0.7.0), the turbo
tier (0.8.0), MCP tool/resource schemas, and unexported internal helpers.

See the [API Reference](/docs/api) for full TypeScript signatures and the
[Changelog](/changelog) for per-release notes.
